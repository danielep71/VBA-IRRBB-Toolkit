# 🏗️ v0.1.0 — Repository foundation

[← Index](README.md) · [GitHub milestone](https://github.com/danielep71/VBA-IRRBB-Toolkit/milestone/1) · [Next: v0.2.0 →](v0.2.0.md)

## 🎯 Purpose

Establish the project's foundation before developing the application:
architecture, baseline contracts, supported environments, source management
rules, and criteria for demonstrating that a change works. The deliverable
is an organized, auditable repository on which later milestones can build
the workbook and models.

## 💡 Why it matters

A numerically plausible model is difficult to verify if its data, units,
authoritative source, or tested version are unclear. The foundation makes
these decisions explicit and separates calculations, Excel integration,
and the public interface. A worksheet or import problem can then be
distinguished from an econometric problem, and each correction can be traced.

## 🛠️ Activities and deliverables

| Area | What is defined | Why it matters |
| --- | --- | --- |
| Architecture | Calculation core independent of Excel, public facade, and workbook adapters | Enables focused testing and clear ownership |
| Host | Target Windows/Excel environment, allowed libraries, and support limits | Prevents compatibility claims without evidence |
| Data | Fields, units, segments, checks, and synthetic cases | Creates a common foundation for the models |
| Models | Initial specifications, expected outputs, sources, and open questions | Exposes decisions that must precede implementation |
| Checks | Static checks, defect regressions, and CI | Detects defects that can be verified in source files |
| Governance | PRs, priority, assignment, milestones, licensing, and provenance | Connects work, ownership, and evidence |

Exported VBA will be the authoritative source. Any executable workbook must
be built from those sources. The evidence protocol distinguishes static
inspection, Excel compilation, test execution, and independent numerical
verification.

## 🔗 Dependencies and transition to the next phase

The foundation records the owner's initial decisions. On October 9, 2026,
the owner approved moving the template (#5), VBA import/export (#6), and
Excel test harness (#8) to [v0.2.0](v0.2.0.md). Their acceptance criteria
remain mandatory in that phase.

Acceptance of the baseline contracts does not automatically resolve the
methodological amendments: #32 covers data, #33 Rates, #34 Stable, #35
sources and applicability, #36 Decay verification, and #37 model composition.
These dependencies must remain visible after foundation closeout.

## 🔎 Practical example

A developer must be able to determine where to add a mathematical function,
which inputs it receives, how to expose it to the application, and which
evidence belongs in the PR. The developer must also understand that a
passing Python check does not establish that the function compiles or
produces correct results in Excel.

## ✅ Completion criteria

- Architecture, host, data, and model decisions have consistent records
  linked to their acceptance evidence.
- Static checks pass on the final candidate, and blocking review findings
  are resolved with evidence.
- Every open and closed issue has an assignee, a milestone, and exactly one
  priority. Update the automation's default before retiring the milestone.
- Remaining work is complete or explicitly reassigned, with its dependencies
  and acceptance requirements preserved.
- The owner accepts closeout under the
  [dedicated checklist](../FOUNDATION_CLOSEOUT.md).

## 🚧 Delivery boundaries

This milestone does not deliver a validated workbook or certify econometric
models. Defining the evidence protocol is not the same as executing it.
Publication, distribution, and visibility remain separate decisions; the
roadmap documentation does not change those settings.
